# Vapor Target Build Snapshots and VPS-Hosted VM Builders Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Let Vapor install one VPS-built, authenticated Cargo target snapshot for each supported target, produced inside VPS-hosted target-native VMs under the single rolling Vapor/toolchain locks.

**Architecture:** A separate Build Cache service owns current snapshot manifests and bytes. The single VPS orchestrates two isolated virtual machines using the same VM lifecycle: a pinned Linux guest for the Linux target and a pinned Windows guest for the Windows target. The client selects only by target triple and verifies the signed manifest before restoring into its shared target root. No other server or human desktop is an official build dependency, and no silent client-side cold-build fallback is supported.

**Tech Stack:** Rust, Axum, signed JSON manifests, streamed archive transfer, VPS-hosted Linux and Windows VMs managed through one orchestration path, existing Platform deployment/export composition, Cargo and the Vapor-managed toolchain.

## Global Constraints

- There is one ecosystem-level Vapor.lock, one canonical toolchain lock, and one target-specific build-cache namespace per unique target triple.
- The initially supported targets are `x86_64-unknown-linux-gnu` and `x86_64-pc-windows-gnullvm`, matching the current Vapor app-source manifest; any change is a lock/version change, not an ad hoc cache choice.
- For each supported target, the VPS serves one current prebuilt target snapshot generated by the canonical Vapor-managed build plan.
- The VPS is the build orchestrator and sole publisher of official snapshots.
- Both target lanes run in VMs hosted by the one VPS and provisioned, started, stopped, updated, and monitored by the same VPS-owned orchestration mechanism.
- The Linux guest image, guest toolchain environment, and libc baseline are locked; the Windows guest image and guest toolchain environment are also locked.
- The Windows guest is hosted on the VPS; there is no separate Windows server/worker and no owner-PC fallback. Linux cross-build output is not treated as a Windows developer snapshot.
- VPS preflight verifies that its provider/host supports the required virtualization and resource budgets. If it does not, builds remain unavailable until the VPS is upgraded or replaced; orchestration never silently moves work elsewhere.
- A missing, stale, or corrupt snapshot is a setup failure with a repair/retry path, not a silent local cold-build fallback.
- Clients outside the single supported rolling Vapor state are rejected; the snapshot service exposes no compatibility cache generation for older clients.
- The Platform Server composes and deploys a separate Build Cache service; cache policy and bytes remain service-owned.
- A clean second-home restore followed by canonical build commands must not unexpectedly recompile the full workspace.

## Review Focus

- Client selects a target not supported by current server snapshot — setup fails with supported-target guidance and does not install another target's archive.
- Manifest target/lock/toolchain does not match the installed Vapor state — verification rejects before extraction.
- Archive is corrupt, truncated, or contains path traversal/link entries — verification rejects and leaves the existing target root intact.
- Build or publication is interrupted — the previous current snapshot remains available until the replacement is fully validated and atomically promoted.
- Either VPS-hosted target VM cannot start, has the wrong pinned image, or lacks its resource budget — that target becomes unavailable; no snapshot is published and no external worker or desktop build is substituted.

**Interfaces:**
- `GET /v1/targets/{target}/current/manifest.json` requires `X-Vapor-Client-Version`, `X-Vapor-Lock-SHA256`, and `X-Vapor-Toolchain-Lock-SHA256`; it returns the signed current manifest, `404` when no snapshot exists, or `426 Upgrade Required` when any client lock identity is stale.

- `POST /v1/internal/targets/{target}/candidate` accepts only a narrowly authenticated builder principal and stages a candidate for validation/promotion.

## Promotion policy

The official endpoint exposes only the current snapshot per target. Publication
is authorized, validated, and atomic. The service does not expose an arbitrary
version selector, old cache generations, or a human-machine publishing path.
